### 10.2 Replay correctness: two distinct comparisons

The replay contract in §2 and AC-1 is clarified as follows. These are separate assertions and must never be conflated:

1. **Within-arm replay correctness (hard gate):** for each arm independently (Q31 and FPE), replay the captured production decision function from a complete snapshot of that arm's operands and mutable state. The replay must reproduce that arm's production return value and all compared post-call state exactly (`==` for suitable discrete fields and `to_bits()` for floating-point fields). This validates capture/replay fidelity.
2. **Cross-arm differential classification (R2.2 subject):** compare the Q31 and FPE production outcomes and state. Differences are retained and classified using R/A/S/P/F and the stage sub-flags. Cross-arm identity is **not** a blanket acceptance requirement; a difference is neither hidden nor automatically accepted. It must be classified, attributed, and handled by the applicable acceptance criterion and owner disposition.

Accordingly, replace the §2 table's “Replay-equality assertion” row with: “Within each arm, replay equals that arm's captured production result and post-call state bit-for-bit; Q31-versus-FPE differences are separately classified and attributed under §3.” AC-1 means within-arm replay correctness for both arms plus complete cross-arm differential capture/classification; it does not require unconditional Q31/FPE bit identity.

The canonical class vocabulary is **R/A/S/P/F** throughout. Replace every occurrence of `R/I/S` with `R/A/S`.

Keep two different propagation concepts separate:

- **Within-frame downstream propagation (`P`):** a structural decision difference at a later stage in the same frame, linked to the earliest attributable upstream R/A/S event in that frame.
- **Cross-frame recurrence/cascade (D-6):** evolution of the recurrence state across successive frames. This is reported by the persistence/recurrence analysis and must not be conflated with the within-frame `P` annotation.

If a later-stage difference cannot be linked to an earlier same-frame event, record it as `Unattributed`; do not force an attribution. Cross-frame recurrence records reference the frame sequence and recurrence-state key explicitly.

### 10.5 D-6 recurrence record and outcome semantics

The D-6 implementation must define and retain, before interpreting results:

- the complete recurrence-state key (all fields whose equality is necessary to establish that the relevant recurrence has returned to a prior state);
- the exact equality method for each key field, including bitwise equality for floating-point state where applicable;
- the maximum cycle period searched (`K`), declared as an explicit configuration/constant and reported in the bundle;
- the observation horizon and the exact frame interval examined;
- the serialized recurrence state or stable digest plus enough retained state to independently verify any reported match.

Each material/chain outcome is exactly one of:

- `FixedPointObserved` — the recurrence state equals the immediately preceding recurrence state;
- `CycleObserved` — a prior recurrence state repeats with a reported period in `2..=K`;
- `BoundedNotTerminated` — no fixed point or cycle within the configured search and observation horizon.

`BoundedNotTerminated` is not a failure, is not evidence of general non-termination, and must not be described as termination. The report must not imply that a period greater than K was ruled out. K is a search bound, not a mathematical claim about the encoder. The five-frame OD-3 isolated boundary replay remains separately retained.

The machine-readable per-frame records are authoritative. `chains.md` provides the concise human-readable recurrence summary and references exact machine-readable row IDs. The summary must include K, observation horizon, state-key definition/version, outcome, and any limitations.

### 10.6 Coverage applicability matrix

Extend AC-2 with an explicit per-operating-point applicability matrix over the requested dimensions (window type, transition type, and state-carrier path):

- Every applicable combination must have at least one observed execution and a hard assertion that the path was reached.
- Every inapplicable combination must be explicitly recorded as `NotApplicable` with a concrete reason tied to the operating point or production path.
- Missing, unwired, unsupported, or unobserved combinations are not `NotApplicable` by default and never count as coverage.
- Aggregate `seen()` checks must be derived from this matrix; a vacuous or globally aggregated pass cannot substitute for per-OP evidence.

This preserves the M2 coverage-accounting discipline while avoiding a requirement to exercise combinations that cannot occur in a given operating point.
