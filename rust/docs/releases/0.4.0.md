# Ferrite 0.4.0 — release notes (crates.io release, 2026-11-16)

> **Status: source-only release.** The repository and the crates.io packages
> ship the complete source; no prebuilt binaries are distributed and none are
> advertised below. FDK-AAC redistribution conditions and AAC patent review
> remain matters for qualified assessment before any binary distribution (see
> `0.1.0-third-party-audit.md`); nothing here claims legal or patent
> clearance. Human/legal sign-off of the converter third-party inventory
> remains outstanding (see `rust/convert/THIRD-PARTY-NOTICES.md`).

## 1. What this release is

Ferrite 0.4.0 is the sixth source release of the native Rust audio project
and the first release published to crates.io from an automated, tokenless
pipeline (crates.io Trusted Publishing through GitHub Actions). Both crates
move to 0.4.0 together, following the release-train convention established
by 0.3.2 (`ferrite-aac` 0.3.2 → 0.4.0; `aac-convert` 0.3.3 → 0.4.0).

- **`ferrite-aac` 0.3.2 → 0.4.0** carries the release's substance: SIMD
  (NEON and AVX2) quantization kernels with runtime dispatch, the R1
  single-quantization S4→QC pipeline restructuring, and the supporting
  benchmark/validation infrastructure. The public API is unchanged — every
  new module is `pub(crate)` and cfg-gated, and the supported surface
  (`aac_enc::{config, channel_map, encoder}`) is untouched. The minor (not
  patch) bump is deliberate: R1 and SIMD dispatch change encoder internals,
  and a minor release keeps `^0.3` dependents from silently picking up the
  new engine.
- **`aac-convert` 0.3.3 → 0.4.0** tracks the encoder: its `ferrite-aac`
  dependency requirement moves to `0.4.0` and its `ebur128` pin moves to
  `=0.1.11` (already merged after 0.3.3). No converter feature work is in
  this release.

Encoder scope is unchanged: AAC-LC only, VBR-1 through VBR-6 selectable,
VBR-6 the default, mono/stereo at 44.1 kHz and 48 kHz, 16-bit PCM input,
ADTS or M4A output, no resampling or downmixing.

## 2. Highlights

### SIMD-accelerated quantization (ARM64 NEON and x86-64 AVX2)

- The S3 quantizer hot kernels (`quantize_lines`, `calc_sfb_dist`,
  `calc_sfb_quant_energy_and_dist`) are vectorized four lines at a time on
  AArch64 (NEON) and eight lines at a time on x86-64 (AVX2), re-derived for
  Ferrite's Q31 fixed-point semantics.
- Runtime dispatch with scalar fallback: AArch64 always uses NEON;
  x86-64 uses AVX2 only after an `is_x86_feature_detected!("avx2")` check;
  every other target — and every exceptional input, tail, or saturating
  case — takes the scalar reference path, which remains the semantic
  authority.
- SIMD and scalar paths are asserted bit-identical by dedicated kernel
  regression tests on both architectures; encoded output does not change
  with the dispatch decision.

### Single-quantization S4→QC pipeline (R1)

Before R1, every frame quantized the spectrum twice (once in the S4
scalefactor search, once again in QC pass 0) and computed a dead S5
QMAX/sectioning stage whose results were never consumed. R1 removes both
redundancies:

- The dead S5 stage is deleted.
- QC pass 0 is seeded with the S4 winning quantization instead of
  re-quantizing; every gain-loop retry still quantizes fresh, exactly as
  before.
- Scalefactor step 3 now re-quantizes the bands it moves (deferred step-3
  re-quantization), restoring the stored gain/line invariant the seed
  relies on.
- The `MAX_QUANT` early-out fallback is preserved by construction: a seed
  that contains an early-out trigger keeps that trigger, QC recomputes
  per-band maxima before bit counting, and the standard gain-bump retry
  replaces the complete band. Residual suppression uncertainty is
  documented and explicitly risk-accepted in the code.
- Four differential regression tests cover the S4-winner/seed identity on
  the committed corpora, seeded-vs-fresh frame equality (including pass
  counts and bit totals), the forced early-out fallback, and a
  line-changing step-3 move through the real estimator.

R1 is designed and regression-tested to preserve encoder decisions and
encoded output; it is a performance change, not an algorithm change.

### Performance

Performance statements are separated by evidence class:

- **Measured (formal campaign):** ARM64 NEON quantization produced a
  **+14.576 % median end-to-end improvement** at VBR-5 in the documented
  native ARM64 A/B campaign (16 instrumented pairs, all 16 pairs faster,
  all four formal fixtures improved, no regression; performance baseline
  §39). This is a measured, accepted result.
- **Preliminary (directional only):** R1 produced an improvement of
  approximately **5.18 % on one music fixture across three rotating
  rounds** in a preliminary session measurement. This is a directional
  result only — it is not the formal paired A/B campaign that the NEON
  acceptance went through, and it must not be cited as a validated
  benchmark. A formal R1 campaign has not been run.
- **No AVX2 performance claim.** Native AVX2 correctness is validated
  (§36); its end-to-end performance campaign remains blocked — no native
  x86-64 measurement was taken (§40). Blocked is not a performance result.

### Conversion tool

No new `aac-convert` features are introduced by 0.4.0; installing 0.4.0
delivers the full current converter surface consolidated during the 0.3.x
line: FLAC-to-M4A/ADTS single-file and parallel batch conversion, artwork
discovery and album-folder artwork reuse, structured live progress
reporting on stderr with machine-readable per-file results on stdout,
fast-start (optimized) M4A output, ReplayGain 2.0 / `iTunNORM` loudness
tagging, gapless signalling, `--skip-existing` safe reruns, and dry-run
planning.

### Packaging and publication

- Release publication moves to crates.io **Trusted Publishing**: a
  tag-triggered GitHub Actions workflow authenticates with a short-lived
  OIDC token via `rust-lang/crates-io-auth-action@v1`; no long-lived
  registry token is stored in the repository.
- crates.io metadata completed on both crates: `documentation` links
  (docs.rs, where both crates build today), `categories`, and converter
  `keywords`/`readme` declarations. No homepage URL was invented.

## 4. Known limitations

- **Encoder scope limits unchanged**: AAC-LC only, 44.1/48 kHz mono/stereo,
  16-bit encoder input, no resampling or downmixing, no universal
  gapless-playback claim.
- **AVX2 performance unmeasured**: correctness-validated only; the
  end-to-end campaign needs native x86-64 hardware or an authorized native
  CI runner. No speedup or regression conclusion exists for AVX2.
- **R1 evidence is directional**: the ~5.18 % music-fixture result comes
  from a preliminary rotating-rounds session measurement, not the formal
  paired campaign; treat it as indicative only.
- **MSRV 1.99.1** (unchanged).
- **Legal/notice sign-off outstanding** (unchanged): the converter
  third-party inventory still needs human/legal review before binary
  distribution; the FDK-AAC license grants no patent license.

## 5. Build and installation

Install from crates.io (Rust 1.99.1):

```sh
cargo install aac-convert          # converter binary; pulls in ferrite-aac 0.4.0
```

Use the encoder as a library:

```toml
[dependencies]
ferrite-aac = "0.4.0"
```

Build from a repository checkout (what CI exercises):

```sh
git clone https://github.com/whepper/ferrite.git
cd ferrite && git checkout v0.4.0
cd rust
cargo build --locked --release -p aac-convert   # binary: target/release/aac-convert
cargo test --locked -p aac-convert              # app suite incl. M4A/ADTS checks
```

No C toolchain or FFmpeg is required for builds (FFmpeg is
verification-only). SIMD selection is automatic at runtime; no cargo
feature flags are involved.

**Publication order (release execution only):** `ferrite-aac` 0.4.0 must be
published before `aac-convert` 0.4.0, whose manifest requires
`ferrite-aac = "0.4.0"`. Consequently `cargo publish --dry-run
-p aac-convert` can only succeed once `ferrite-aac` 0.4.0 is live on
crates.io; its local dry-run at release-preparation time is expected to
fail dependency resolution for exactly that reason, and the packaged
artifact is instead verified with `cargo package --locked` plus a manifest
inspection that the `ferrite-aac` requirement is version-only (no path
leak).

## 6. Licensing and distribution status

Unchanged from 0.3.3: `ferrite-aac` is FDK-AAC-licensed with the complete
license text, `NOTICE`, and per-file attribution headers in the package;
`aac-convert` is `MIT OR Apache-2.0` with complete license texts and an
explicit licensing-boundary statement — depending on `ferrite-aac` does not
place converter source under FDK-AAC, while distributed converter binaries
remain subject to the FDK-AAC conditions for the linked codec dependency. No
binary is distributed by this release. These notes make no legal or
patent-safety claim.
