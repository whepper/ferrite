# Ferrite 0.3.1 — release notes (source-only release, 2026-11-14)

> **Status: source-only release.** The repository ships the complete source
> tree; no prebuilt binaries are distributed and none are advertised below.
> FDK-AAC redistribution conditions and AAC patent review remain matters for
> qualified assessment before any binary distribution (see
> `0.1.0-third-party-audit.md`); nothing here claims legal or patent
> clearance.

## 1. What this release is

Ferrite 0.3.1 is the fourth source release of the native Rust audio project:
the float-native AAC-LC encoder derived from the Fraunhofer FDK AAC codebase
(`ferrite-aac` / `ferrite_aac`) and its reference consumer, the FLAC-to-M4A
converter `aac-convert`.

This is a converter-side release. The encoder is unchanged since 0.3.0:
VBR-1 through VBR-6 remain selectable, VBR-5 remains the upstream-compatible
baseline (byte-identical to 0.2.0), VBR-6 (VBR-5 with a 20 000 Hz configured
bandwidth) remains the Ferrite default, and no encoder algorithm,
psychoacoustic decision rule, quantization or bitstream change is part of this
release. What changes is everything around the encode: album artwork is
discovered and reused before embedded pictures are consulted, batch
preparation and encoding report structured progress events, the CLI renders
live preparation and encoding progress, and artwork memory use is bounded with
disk staging.

## 2. Highlights

### Artwork discovery and reuse

- **Existing album artwork is reused.** Before embedded FLAC pictures are
  considered, the batch pipeline (and single-file conversion, whose parent
  directory is its one-member album) looks for a conventional image file in
  the source album directory. The search is deterministic: `cover`, `folder`,
  `front`, `album` with `.jpg`, then the same four stems with `.jpeg`, then
  `.png`, then `.webp`. Matching is ASCII case-insensitive; the first
  readable, supported file within the 16 MiB cover limit wins for the whole
  album directory. Missing, unreadable, empty, misnamed or oversized
  candidates are skipped without failing the album.
- **Format handling follows the container.** Formats are detected by magic
  bytes only (never by extension or declared MIME type): JPEG, PNG and WebP.
  JPEG and PNG can be embedded in M4A and published externally; WebP is
  external-publication only (`cover.webp`) because the M4A `covr` atom
  supports JPEG and PNG only. Images are never decoded, recompressed or
  resized. JPEG/`.jpeg` extension support is new in this release alongside the
  discovery pass itself.
- **Embedded fallback is retained.** When no suitable album file exists, the
  pre-existing embedded-picture selection (front cover, then other typed
  pictures, then untyped, in source order) applies unchanged, and embedded
  conflict detection across tracks in one output directory is retained for
  that path. External-only mode with an existing album image no longer reads
  embedded pictures at all: the external file is authoritative.
- **Bounded memory, disk staging.** Resolution happens once per album
  directory, never once per file. Artwork adds at most one image (up to the
  16 MiB cover limit) per in-flight worker for embedding, plus small
  per-album metadata; no per-album image bytes are retained in RAM. Selected
  embedded fallback covers are spilled to a temporary staging directory (one
  file per album, `.aac-convert-artwork-*.tmp.d`, removed on completion) and
  reloaded on demand.

### Preparation and encoding progress

- **Structured, renderer-agnostic progress events.** The new public library
  module `aac_convert::progress` reports `ProgressEvent` values through a
  caller-supplied observer: plan counts (`BatchStarted`), preparation
  lifecycle (`PreparationStarted`, `ArtworkStarted`/`ArtworkFinished` with
  per-album source, `LoudnessFinished` with per-file outcome,
  `PreparationFinished` with tallies), and encoding outcomes
  (`EncodingStarted`, `FileStarted`, `FileConverted`, `FileSkipped`,
  `FileFailed`, `FilePlanned`). The core never performs terminal I/O, so the
  same stream can drive the CLI renderer, a future desktop GUI, or a test
  harness without duplicating conversion logic.
- **Live CLI progress.** The terminal renderer (binary-only
  `cli_progress::ProgressDisplay`) prints a preparation section (album
  artwork discovery with per-album reused/extracted detail, loudness
  analysis with per-file outcomes, reused/extracted/prepared tallies) and an
  encoding section (running file counter with ETA and a converted/skipped/
  failed tally). Interactive terminals get a single updating live line
  (truncated display-only to fit narrow terminals); redirected output gets
  milestone lines throttled to ten-percent steps with a one-second fallback,
  always at completion. A run with no preparation work (for example ADTS
  output) prints a `Converting …` header instead. `--verbose` adds per-file
  `encoding`/`done`/`skipped`/`failed`/`planned` lines; `--quiet` suppresses
  progress while diagnostics still print, including under broken pipes.
- **Concurrency is stage-bounded, never nested.** Preparation resolves album
  artwork once per source directory and then runs loudness analysis; only
  then does conversion run. Each sub-stage uses at most `--jobs` workers and
  finishes before the next begins, so the global worker limit is never
  exceeded. Per-file results stay in deterministic plan order; only progress
  event arrival order follows completion. The legacy `BatchEvent` callback
  and `execute_plan_with_options_and_progress` are retained; the new
  `execute_plan_with_options_and_events` exposes the structured stream.

### CLI behavior and compatibility

- The machine-readable standard-output contract is unchanged: per-file
  `ok`/`skip`/`fail` lines in plan order, the `batch:` header, ignored-entry and tag-diagnostic lines in verbose
  mode, and the final `summary:`/`dry-run:` line. Exit codes, option syntax
  and the no-overwrite publication rule are unchanged.
- The standard-error progress format changed: the old
  `preparing N files (…)` / `[ i/n] path encoding...` / `done` lines are
  replaced by the preparation/encoding sections described above. Scripts that
  parse stderr progress output need updating; scripts that parse stdout are
  unaffected. Version output remains on standard error, now
  `aac-convert 0.3.1`, and M4A `©too` identification moves to
  `Ferrite 0.3.1`.
- `--cover-art` semantics are extended, not replaced: `embedded` (default),
  `external` and `both` keep their meanings, but album-folder images are now
  reused first and WebP album art is published as `cover.webp` in
  `external`/`both` modes. Publication still never overwrites an existing
  `cover.jpg`/`cover.png`/`cover.webp`.
- Documentation caught up with the behavior: the converter reference
  (`rust/convert/README.md`), the user manual (`rust/docs/user-manual.md`)
  and the integration contract
  (`rust/docs/aac-convert-integration-contract.md`) now describe album
  discovery, WebP handling, the new progress display and the memory bounds.
  The authoritative cover-art behavior contract
  (`docs/aac-convert-s1.3-cover-art-final-spec.md`) carries a dated addendum
  recording the change. The root README is repositioned around the Ferrite
  encoder application.

## 3. Artwork discovery and reuse behavior

Single-file conversion resolves artwork the same way as batch mode: the input
file's parent directory is treated as its one-member album, so a `cover.jpg`
(or `.jpeg`/`.png`/`.webp` equivalent) beside a single FLAC is reused for
embedding and/or external publication before embedded pictures are read.

Discovery reads each candidate directory listing once, compares names by raw
bytes with ASCII case-insensitivity, pre-checks size and regular-file status,
then performs a bounded read capped just above the 16 MiB limit — so a file
that grows between the size pre-check and the read cannot cause an unbounded
allocation. A concurrently replaced path that is not a regular file is
skipped to the next candidate; a residual FIFO-swap blocking risk on open is
accepted and documented at the discovery site. Validation is intentionally
shallow (magic-byte prefix/signature match, no image decode, no added image
dependency): a file with a valid prefix but corrupt payload is treated as its
sniffed format, matching the pre-existing embedded-artwork policy.

Per-album outcomes are observable: `ArtworkFinished.source` reports
`ExistingFile` (with the reused path), `Embedded`, or `None`, and the
preparation tally distinguishes reused from extracted albums. All conflict and
publication problems warn without failing audio.

## 4. Preparation and encoding progress improvements

Preparation previously emitted a single `preparing N files (…)` line and
encoding emitted one line per file. The pipeline now reports per-album
artwork discovery (started/finished with source and running reused/extracted
counts), per-file loudness completion (`Analyzed`, `Unmeasurable`, `Failed`),
preparation tallies (prepared/failed/skipped plus artwork reuse counts), and
per-file encoding outcomes — all as data, with rendering confined to the
binary. `ProgressState` accumulates absolute counters that stay correct
regardless of worker completion order; event callbacks always run on the
calling thread while workers only send messages, so progress output is never
interleaved.

The bounded-concurrency helpers (`parallel::map_indexed_with_events`, and the
loudness pre-pass built on them) complete albums out of order under
`--jobs N` but merge results in plan order, so summaries and stdout reporting
stay deterministic. `--jobs 1` restores strictly sequential execution and
plan-ordered events.

## 5. CLI behavior and compatibility notes

Existing conversion commands continue to work, with the stderr progress
format change noted in §2 as the one observable break for stderr parsers:

- **Default output is unchanged from 0.3.0.** Default conversion still
  selects VBR-6; explicit `--vbr 5` still selects the upstream-compatible
  baseline. Neither the default nor the VBR-5 bytestream changed in this
  release (no encoder change).
- **Album artwork may now change M4A outputs.** A directory that contains a
  conventional image file (`cover.jpg` and friends) will now embed and/or
  publish that image where 0.3.0 used embedded pictures or wrote nothing.
  Conversions that must reproduce 0.3.0 artwork selection exactly should run
  in directories without such files, or with `--no-tags`/ADTS where artwork
  is inert.
- **Stdout, exit codes and publication guarantees are unchanged.**
  Per-file `ok`/`skip`/`fail` lines, the `summary:` line, exit codes 0/1/2,
  verbose/quiet semantics (modulo the new progress rendering), dry-run plan
  output, `--skip-existing` behavior and atomic no-overwrite publication are
  all unchanged.
- **Rust API is additive.** The new `progress` module, `ArtworkSource`,
  `LoudnessOutcome`, `ProgressState`, and
  `execute_plan_with_options_and_events` are additions; `BatchEvent`,
  `execute_plan_with_options_and_progress` and all existing conversion entry
  points keep their signatures and behavior (single-file entry points without
  cover-art parameters remain embedded-only).

## 6. Public progress API implications

The progress event stream is designed to be consumed by more than the CLI:
because the library performs no terminal I/O and depends on no progress or
TUI crate, the same `ProgressEvent` values can drive a future desktop GUI
(Tauri/React, Slint), or any embedding that needs per-album and per-file
preparation detail plus encoding outcomes, without duplicating conversion
logic. No desktop GUI is implemented in this release, and none is advertised:
the only renderer shipped is the terminal display. `ProgressEvent` is
`#[non_exhaustive]` so future variants cannot break the CLI renderer.

### Tests not executed here (BLOCKED)

Eleven tests require external artifacts that are not available in this
environment and fail loudly naming the missing variable/artifact: ten need
the private FDK-AAC reference checkout (nine `phase1*` C-oracle parity tests
plus `m55_streams_match_c_reference`), and `m5a_decode_check` needs an

those tests passed.** No substitute reference implementation was used. They
remain mandatory in an environment that holds the private reference checkout
and the decoder binary. Unchanged from 0.3.0: no encoder change since means
no new oracle evidence was required.

## 8. Known limitations

- **Private Tier-B oracle validation remains unavailable** (see §7).
  Compensating evidence: the unchanged 20-point C init parity, committed
  byte/hash baselines, and decoder-tool acceptance (ffprobe, afinfo).
- **No perceptual superiority claim is made for VBR-6** (unchanged from
  0.3.0): the 20 kHz bandwidth is validated as configuration and decoded
  spectral behaviour only. No listening test, ABX test or perceptual metric
  is part of this release, and none may be inferred. No encoder algorithm
  change occurred, so no perceptual change is claimed either.
- **HE-AAC v1/v2, SBR and PS are not implemented** (unchanged): AAC-LC only,
  no CBR mode, no SBR/PS signalling, no HE-AAC output.
- **Ferrite is not bit-exact with FDK AAC** (unchanged): the port matches the
  reference at the validated initialisation points and reproduces the
  committed baselines; no general bit-exactness claim is made.
- **Production matrix** (unchanged): 44.1/48 kHz, mono/stereo, 16-bit encoder
  input (24-bit FLAC truncated without dithering), ADTS or M4A output, no
  resampling or downmixing.
- **VBR-3 transient observation** (unchanged, recorded, unexplained at the
  perceptual level, deferred to a future quality evaluation).
- **`esds` bitrate fields are 0/0** (unchanged): unknown rather than nominal;
  players ignore these fields.
- **No standalone `aac-convert` package** (unchanged): its path dependency
  on the unpublished `ferrite-aac` crate cannot resolve against crates.io;
  the supported distribution model is a workspace source bundle. Neither
  crate is published to a registry by this release.
- **No desktop GUI exists.** The progress event stream is built to support
  one in the future (§6), but 0.3.1 ships the terminal renderer only.
- **Stderr progress parsing is the one CLI-format break** (§5): the old
  per-file `encoding...`/`done` stderr lines are replaced by the
  preparation/encoding sections; stdout parsing is unaffected.
- **Discovery edge case (documented at the site):** a candidate path swapped
  for a FIFO between listing and open could block on open; unreadable,
  non-regular, empty, unsupported or oversized candidates are otherwise
  skipped to the next candidate without failing the album.

## 9. Build and installation

Source-bundle model (no registry publish while `ferrite-aac` is an
unpublished path dependency). From `rust/` with toolchain 1.99.1:

```sh
cargo build --locked --release -p aac-convert   # binary: target/release/aac-convert
cargo test --locked -p aac-convert              # app suite incl. M4A/ADTS/artwork/progress checks
cargo test --locked --features aac_enc --lib    # encoder suite (Tier-B tests BLOCKED here)
```

Dependencies resolve from crates.io against the committed `Cargo.lock`; no
vendoring is needed and no dependency versions changed in this release. No C
toolchain or FFmpeg is required for builds (FFmpeg is verification-only).

## 10. Licensing and distribution status

Ferrite remains a Third-Party Modified Version of the Fraunhofer FDK AAC
Codec Library for Android (modification notice dated 2026-10-26). This
source-only release ships the complete license text (`rust/NOTICE`,
`rust/LICENSE-FDK-AAC`) in the `ferrite-aac` package and retains all per-file
notices and the third-party inventory (`0.1.0-third-party-audit.md`), which
is unchanged for 0.3.1 because no dependencies were added, removed or
upgraded. New Ferrite-authored files (artwork discovery, progress events,
CLI progress rendering, bounded-concurrency helpers and their tests) follow
the repository's new-file notice policy; upstream-derived files retain their
complete headers.

No binary is distributed, so binary-redistribution terms are not exercised;
they — like AAC patent authorization, for which FDK grants **no patent
license** — need separate qualified assessment before any binary
distribution. These notes make no legal or patent-safety claim.
